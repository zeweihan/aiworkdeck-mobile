# 移动端开发制度（四端对齐）

生效日期 2026-09-13（dev-board#427/#426 复盘后由用户要求建立）。本文是**每一条移动端开发指示**的处理规程，
与仓根 `CLAUDE.md` 的契约规矩并列，会话开始接到指示时先按这里走。

## 1. 四端矩阵先于代码

接到任何功能指示（无论用户点名哪一端），动手前先填这张表并写进看板卡正文：

| 端 | 涉及？ | 本次做 / 延后 / 不适用 | 理由（延后与不适用必须写） |
|---|---|---|---|
| iOS | | | |
| 微信小程序 | | | |
| 安卓 | | | |
| 鸿蒙 | | | |

规则：
- **默认四端都涉及**。「不适用」只允许两类理由：平台没有该能力（如 iOS 微信无沙箱、鸿蒙无支付通道）、
  或用户明确说只做某端。「延后」必须写清卡在什么外部条件上（商户号、开放平台审核、协议签署）以及谁去解锁。
- 涉及多端时**一张卡一端**（看板「一个问题 = 一个 issue」），主卡里链接子卡；一端做完不算完，
  主卡要等全部子卡到「待复测」才转「待复测」。
- 能力矩阵的唯一来源是 `contract/capabilities.json`。某端暂不支持的功能也要在该端**可见地说明**
  （入口 + 提示文案），不能默默不渲染让用户找不到——这是 2026-09-09「充值在哪」事故的教训。

## 2. 交付定义

一端「做完」的定义（缺一项就不能报「完成」，要标「未验证」）：

1. 契约先改（`contract/`）、生成物入仓、`check.mjs` 绿；
2. 该端单测绿，命令与输出原文进汇报；
3. **从该端首页走一遍用户路径到新功能并截图**（模拟器 / 开发者工具 / 真机），截图路径进汇报；
   新用户态（未登录、未绑定、余额为 0）必须单独走一遍，入口不得依赖老用户才有的状态；
4. 涉及服务端的，线上端点用假参数打一次拿到预期错误码（证明链路通到位）；
5. 看板卡落实记录含「复测提示」：用户在真机上按哪几步能看到结果。

## 3. 派工与验收

- 主会话（Fable）写规格、拆卡、开任务书、审 diff 与截图、提交合并发版、写落实记录；不写业务代码。
- 每端一个子代理，跨端契约改动集中在一个代理避免冲突；服务端（官网 / Java）各一个代理并行。
- 子代理报告必须含：改动清单、验证命令与输出原文、截图路径、假设与未验证项。主会话对「未验证项」逐条决定：
  自己补验、让用户复测、或明确标注后上线。
- 真机才能验证的项（支付、相机、推送）在落实记录里**明确写「等真机复测」**，不写「通过」。

## 4. 发版与提审

- 小程序：`node scripts/mp-upload.js <版本> "<备注>"` → 用户设体验版复测 → 通过后用户提审。
- iOS：往 main 推 `[appstore]` 提交走 CI 出包到 TestFlight；ASC 版本、内购元数据、提审由主会话经 API 完成；
  涉及内购的版本必须把 IAP 附在同一版本提交。
- 安卓 / 鸿蒙：暂无商店上架通道时，出包到 `dist/` 并在卡上给安装方式；用户无设备时如实记「未真机验证」。
- 四端版本号各走各的序列（见记忆 mobile-release-recipe），但同一功能的四端发版要在主卡里列成一张表。

## 5. 外部前置条件登记

支付、推送、登录等依赖外部账号的能力，先查 `EXTERNAL_SERVICES.md` 与 `docs/ops/` 的开通手册；
卡在用户动作上的，在卡里写「等用户：具体做什么、在哪个后台、预计多久」，并在对用户汇报时单独列出，不混在技术细节里。
